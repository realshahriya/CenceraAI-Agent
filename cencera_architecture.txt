Document Purpose
This document is the single source of truth for how Cencera is built, how every component connects, and why each design decision was made. It is written for engineers building the system and should leave no implementation question unanswered at the architectural level.
Cencera is a protocol-grade trust and reputation infrastructure for Web3. It is designed to be consumed by the largest decentralized applications in the world — platforms like Uniswap, Aave, Phantom, MetaMask, and PumpFun — and must therefore meet the standards those platforms require: sub-second API response times, 99.99% uptime, cryptographically auditable outputs, and a scoring model that behaves predictably and cannot be gamed without immediate detection.
This is not a transaction screening tool. It is not a blacklist. It is a persistent, learning intelligence layer that assigns every blockchain entity a continuously updated trust state derived from its full behavioral history across on-chain activity, market dynamics, off-chain signals, and AI-derived pattern analysis. Platforms consume that trust state to make autonomous, risk-aware decisions.

1. Core Design Principles
Before any component is described, these principles govern every decision. Any feature, integration, or optimization that violates these principles must be rejected.
1.1 Trust Is a First-Class Data Primitive
Trust is not a feature or an output. It is the core data type that Cencera manages. Every architectural decision is made in service of making trust scores accurate, timely, explainable, and tamper-resistant. Trust scores must be versioned, auditable, and reproducible — meaning that given the same input signals and the same model version, the same score must always be produced.
1.2 Scores Are Probabilistic, Not Absolute
A trust score is a probabilistic estimate of how consistent an entity’s behavior is with known-safe or known-malicious patterns. A score of 85 does not mean the entity is safe. It means the current evidence strongly suggests safe behavior. Consuming platforms are responsible for acting on that probability according to their own risk tolerance. Cencera must communicate this clearly in every API response.
1.3 The System Must Degrade Gracefully
When data sources are unavailable, when a new entity has no history, or when a platform disables certain signal groups, the system must still produce a valid output. That output must be clearly labeled with its confidence level and the active signals used to produce it. A partially-informed score that is honestly labeled is infinitely more valuable than refusing to score or silently returning a neutral result.
1.4 Explainability Is a Security Risk and Must Be Tiered
The same explanation system that builds trust with legitimate users is a roadmap for adversaries. If the API tells an attacker which specific signals drove a negative score, the attacker will engineer their next contract to avoid those signals. Explanations must therefore be detailed enough to be useful but structured so that the most granular signal-level information is only available to verified enterprise partners under contractual controls, not discoverable through public API probing.
1.5 The System Must Learn Continuously
Static rule systems become obsolete within weeks in adversarial Web3 environments. Cencera’s scoring model must have a defined feedback loop connecting confirmed exploit data, human analyst review, and user-reported loss events back into the training pipeline. Every confirmed exploit must retroactively adjust scores for all entities that interacted with or resembled that exploit.
1.6 No Single Point of Failure
The system serves billion-dollar protocols. A database outage, a compromised API key, or a single model failure cannot take down scoring for all consuming platforms. The architecture must be horizontally redundant at every layer, with defined fallback behaviors at each failure point.

2. Entity Model
Everything Cencera scores is an entity. The entity model defines what types of things can be scored, how they are identified, and what lifecycle state they can be in. This is the foundation that all other components build on.
2.1 Entity Types
Cencera scores five entity types. Each type has a distinct risk profile and a distinct set of relevant signals.
Externally Owned Accounts (EOAs)
Standard user wallets. Scored primarily on transaction behavior patterns, approval patterns, interaction history, and historical adjacency to known exploits or legitimate protocols.
Smart Contracts
The highest-risk entity type. Scored on bytecode similarity to known exploits, behavioral patterns since deployment, upgrade history, admin key behavior, and interaction graph patterns.
Tokens (ERC-20, ERC-721, ERC-1155)
Scored on token distribution concentration, liquidity health, supply manipulation patterns, tax and fee behavior, and the trust scores of their deployer addresses.
NFT Collections
Scored on collection contract behavior, marketplace activity authenticity, wash trading indicators, and deployer history.
Protocols and DApps
Composite entity type. A protocol score is derived from the weighted combination of all its constituent contract scores, its TVL risk metrics, its governance structure, and its off-chain identity signals.

2.2 Entity Identification
Each entity is assigned a Cencera Persistent Identifier (CPID) at first observation. The CPID is a stable internal identifier that persists across chain reorgs, contract upgrades, and metadata changes. This is critical because on-chain addresses are reused, proxy contracts are upgraded, and the same logical entity can have multiple addresses. The CPID system allows Cencera to maintain continuous reputation history even when underlying addresses change.
For cross-chain entities — a deployer who operates on Ethereum, Arbitrum, and Base — the system maintains a CPID per chain by default, with an optional cross-chain linkage record that connects them. The scoring engine treats cross-chain linked entities as sharing reputation context, not as independent actors. This closes the attack vector where an adversary builds a clean history on one chain and attacks on another.
2.3 Entity Lifecycle States
Every entity exists in one of four lifecycle states at any time. These states determine how the entity is scored and what information is communicated to consuming platforms.
State 1: Nascent
An entity is Nascent for its first 72 hours or first 50 meaningful interactions, whichever comes later. Nascent entities cannot produce a full trust score. They receive a Limited Score based only on static code analysis (for contracts), deployer trust score, and bytecode similarity to known exploits. The API response for Nascent entities must explicitly label the score as Limited and include the reason. Consuming platforms must configure how they treat Limited Scores separately from full scores.
State 2: Active
The standard state. The entity has sufficient history for the full scoring engine to operate. All four signal groups contribute to the score according to the entity-type weight matrix.
State 3: Flagged
The entity has triggered one or more high-confidence anomaly detectors or has been submitted for human review. Flagged entities automatically receive a provisional score reduction and a Flagged label in the API response. The flag persists until cleared by human review or by sustained subsequent behavior that contradicts the flag trigger.
State 4: Archived
The entity has shown no activity for a defined dormancy period (default 180 days) and holds below a minimum TVL threshold. Archived entities retain their last computed score but are marked as stale. Any new activity immediately moves the entity back to Active state and triggers a full rescore.

3. Data Ingestion Layer
The ingestion layer is responsible for continuously collecting, normalizing, and validating raw signals from all four data domains. It does not compute scores. Its only job is to ensure that clean, timely, and correctly attributed signal data arrives in the signal store.
3.1 Ingestion Architecture
The ingestion layer runs as a set of independent ingestion workers, one per data source or data provider. Each worker is responsible for a single data stream, normalizes its data into the canonical Cencera signal schema, validates the data against that schema, and writes it to the event stream. Workers are stateless and horizontally scalable. If a worker fails or a data provider goes down, the rest of the system continues operating on the signals that are available.
All ingested signals are written to an immutable event log before any processing occurs. This means the full raw signal history is always available for audit, model retraining, and retroactive analysis. The event log is append-only. Nothing is ever deleted from it.
3.2 On-Chain Signal Domain
On-chain signals are the highest-weight domain because they are cryptographically verified, permissionless, and cannot be fabricated. The ingestion workers for on-chain data connect to archival node providers for historical data and to real-time RPC endpoints for live data.
Signals Collected
Transaction frequency and value patterns — raw transaction volume, value distribution, average transaction value, standard deviation of value over rolling time windows
Contract interaction graphs — which addresses interact with which contracts, interaction frequency, and the trust context of neighboring nodes in the graph
Approval and allowance behavior — unlimited approval grants, approval patterns to unverified contracts, and revocation behavior
Liquidity provisioning and withdrawal patterns — LP deposit and withdrawal timing, size relative to pool TVL, and synchronization with price movements
Historical exploit adjacency — whether the entity has directly interacted with, received funds from, or sent funds to known malicious addresses
Contract upgrade events — proxy upgrade calls, implementation changes, admin key transfers
Governance participation — voting patterns, proposal submissions, delegation behavior
3.3 Market Signal Domain
Market signals carry 30% weight for token and protocol entities. They are sourced from DEX liquidity pool data, price oracles, and on-chain trading activity. For EOA and pure smart contract entities where market context is not relevant, the platform can suppress this signal group and the scoring engine will renormalize weights accordingly.
Signals Collected
Liquidity depth and volatility — total liquidity, depth at various price impact levels, liquidity volatility over time
Token distribution and concentration — top holder concentration, Gini coefficient of token distribution, team wallet holding percentage
Slippage and price impact patterns — actual slippage versus expected, unusual price impact events, sandwich attack frequency
Sudden supply or tax changes — mint events outside expected patterns, fee parameter changes, honeypot tax triggers
Price-to-liquidity ratio anomalies — market cap relative to liquidity as an indicator of manipulation risk
3.4 Off-Chain Signal Domain
Off-chain signals carry 15% base weight and provide the social and identity context that purely on-chain data cannot capture. Because off-chain data is inherently less reliable than on-chain data, every off-chain signal is tagged with a confidence score at ingestion time, and that confidence propagates through to the final score.
Signals Collected
Project metadata verification — website registration date, domain age, DNS consistency, registration anonymity
Social account authenticity — account age, follower authenticity scoring, engagement pattern analysis, cross-platform consistency
Developer identity continuity — whether deployer addresses link to persistent developer identities across projects and time
Cross-project linkage analysis — whether the same developer or team has deployed other projects, and what the trust state of those projects is
GitHub and code repository signals — repository age, commit history authenticity, contributor identity consistency, sudden repository deletion or privatization
Audit status — verified audit reports from recognized firms, scope of audit relative to deployed code
3.5 AI-Derived Signal Domain
The AI-derived signal domain is architecturally distinct from the other three. It does not collect raw signals from external sources. Instead, it operates as an analytical layer over the signals already collected by the other three domains, producing derived signals that represent patterns too complex to capture with simple rules. Its real value is in its role as the primary anomaly detection and novel threat identification system.
Derived Signals Produced
Bytecode similarity clustering — new contract bytecode is compared against a continuously updated library of known-malicious and known-safe bytecodes using fuzzy matching. Even heavily obfuscated variants of known exploit contracts can be detected this way.
Behavioral anomaly scoring — the AI layer maintains a behavioral baseline for each entity and produces an anomaly score whenever current behavior deviates significantly from that baseline.
Exploit pattern recognition — interaction sequence patterns associated with known exploit types (reentrancy setups, flash loan attack sequences, governance manipulation patterns) are matched against live transaction streams.
Temporal risk trend analysis — the AI layer tracks whether an entity’s risk indicators have been monotonically increasing over time, which is a reliable predictor of eventual exploit execution.
Novel behavior flagging — when the AI layer encounters a pattern it cannot classify against any known reference, it produces a Novel Behavior Flag that routes the entity to human review while assigning a provisional reduced score.
3.6 Signal Quality and Validation
Every ingested signal passes through a validation pipeline before being written to the event log. The pipeline checks for data completeness, timestamp consistency, value range plausibility, and schema compliance. Signals that fail validation are quarantined and flagged for investigation rather than silently dropped. Silently dropping invalid data would create invisible gaps in the behavioral record that could be exploited by an attacker who manipulates a data source to suppress negative signals.

4. Signal Store and Data Architecture
The signal store is the central nervous system of Cencera. It holds every signal ever ingested, every score ever produced, and every model version ever deployed.
4.1 Storage Layers
Real-Time Signals: Hot Layer
Holds the last 90 days of signals in a low-latency, high-throughput time-series database. This is what the scoring engine reads from during live score computation. Response times from the hot layer must be under 20 milliseconds for any entity query.
Historical Signals: Warm Layer
Holds signals from 90 days to 2 years in a columnar analytical database optimized for range scans and aggregations. This layer serves historical reputation queries, model training data exports, and the retroactive rescore pipeline.
Archival Signals: Cold Layer
Holds all signals older than 2 years in compressed archival storage. Accessed infrequently — primarily for deep historical analysis and regulatory audit requests. Retrieval from cold storage is expected to take minutes, not milliseconds.

4.2 Data Isolation and Security
The signal store is divided into isolated compartments by sensitivity level. Raw signals from public on-chain data are in the least restricted compartment. Enriched signals containing identity linkages and cross-project analysis are in a restricted compartment. The exploit signature library is in the most restricted compartment and is never exposed to the API layer, even in enterprise integrations.
The exploit signature database has additional protections: it is write-protected from the API layer entirely. Any write operation to the exploit signature database triggers an alert and requires multi-party authorization. This prevents an API compromise from poisoning the ground truth that the scoring model is trained on.
4.3 The Immutable Event Log
Separate from the tiered signal store, an immutable event log records every signal write, every score computation, every model version deployment, and every human review action with a cryptographic hash chain. This log cannot be modified after the fact. It exists to answer the question: given that entity X received score Y at time Z, what was the exact set of signals, weights, and model version that produced that score? This is essential for enterprise clients who need to audit scoring decisions and for the team’s own post-incident analysis.

5. Trust Scoring Engine
The scoring engine is the computational core of Cencera. It takes signals from the signal store and produces a trust score for any entity on demand.
5.1 Score Structure
Every trust score is a structured object, not a single number. The score object contains:
Composite Score — the final trust score, expressed as a number from 0 to 100
Confidence Level — a separate indicator of how much evidence the score is based on, ranging from Low (Nascent entities) to High (entities with deep history across all signal groups)
Score Manifest — a machine-readable declaration of which signal groups were active, what weight each carried, and what the lookback period was for this computation
Contribution Breakdown — the category-level contribution of each signal group to the composite score
Triggered Indicators — a list of specific risk patterns that were detected, expressed at category level for public API consumers and at signal level for verified enterprise partners
Score Trajectory — the score at the previous 5 computation points, giving consuming platforms visibility into whether a score is stable, improving, or deteriorating
Lifecycle State — the entity’s current lifecycle state (Nascent, Active, Flagged, Archived)
Computation Metadata — the model version used, the computation timestamp, and the data freshness of the most recently updated signal

5.2 Weight Matrix by Entity Type
Because different entity types have fundamentally different risk profiles, the scoring engine does not apply a single weight distribution to all entities. Instead, each entity type has a defined weight matrix.
EOA (Externally Owned Account)
On-chain behavior: 60%   ·   Market signals: 5%   ·   Off-chain signals: 20%   ·   AI-derived patterns: 15%
Smart Contract
On-chain behavior: 40%   ·   Market signals: 15%   ·   Off-chain signals: 15%   ·   AI-derived patterns: 30%
Token (ERC-20 / ERC-721 / ERC-1155)
On-chain behavior: 30%   ·   Market signals: 40%   ·   Off-chain signals: 20%   ·   AI-derived patterns: 10%
Protocol / DApp
On-chain behavior: 35%   ·   Market signals: 30%   ·   Off-chain signals: 20%   ·   AI-derived patterns: 15%
NFT Collection
On-chain behavior: 40%   ·   Market signals: 30%   ·   Off-chain signals: 20%   ·   AI-derived patterns: 10%

5.3 Adaptive Weight Normalization
When a platform disables a signal group, the weights of the remaining signal groups are renormalized proportionally so they sum to 100%. This is enforced by the scoring engine. However, the composite score produced from a reduced signal set is labeled with a lower confidence level, and the score manifest clearly identifies which groups were active. A score of 75 from a full four-group computation and a score of 75 from a two-group computation are not the same score and must not be treated as equivalent.
5.4 Longitudinal Scoring and Time Decay
Scores are computed from a time-weighted history where older signals have progressively less influence on the current score. The default time decay function gives full weight to signals from the last 30 days, declining linearly to 20% weight for signals at the 90-day mark, and declining further to 5% for signals older than 180 days.
NOTE  Platforms can configure a custom lookback window (30D, 60D, 90D, or custom). For entities above a defined TVL threshold, the scoring engine enforces a minimum lookback of 90 days regardless of platform configuration.
5.5 Exploit Pattern Matching
The scoring engine maintains a continuously updated library of exploit fingerprints. A match at 5% similarity or above triggers a contribution to the risk score. A match at 80% or above triggers a Flagged lifecycle state. Symmetrically, the engine also maintains a library of safe interaction fingerprints. Matching against known-safe patterns increases the composite score.
5.6 Cold Start Scoring
Nascent entities receive a Limited Score computed through a dedicated cold start pathway using bytecode analysis, deployer trust inheritance, and initialization transaction analysis. Limited Scores are always communicated with a Nascent lifecycle state label and a Low confidence level.

6. Learning and Feedback Architecture
A scoring system that cannot learn is a system that attackers can eventually defeat by studying its blind spots.
6.1 Three Feedback Channels
Channel 1: Confirmed Exploit Channel
When the security team confirms a new exploit, it is documented and added to the exploit signature library. This triggers retroactive rescoring of all similar entities, webhook notifications to affected platforms, and immediate addition of the fingerprint to the real-time pattern matching library.
Channel 2: Novel Behavior Review Channel
When the AI layer produces a Novel Behavior Flag, the flagged entity enters the human review queue with a 24-hour triage SLA and a 72-hour full analysis SLA. During review, the entity remains Flagged with a provisional reduced score.
Channel 3: User Loss Report Channel
Loss reports are accepted through the API but never directly modify scores. Reports must include a transaction hash demonstrating an actual on-chain interaction with the reported entity. Reports without a valid transaction reference are rejected. Validated reports elevate the entity’s priority in the human review queue.

6.2 Model Retraining
The scoring model is retrained on a defined schedule: a minor update every two weeks incorporating the latest confirmed exploit data, and a major update quarterly. All model versions are immutably versioned. Every score produced is tagged with the model version that produced it. Deployment is blocked if accuracy on the validation set falls below defined thresholds.
6.3 Retroactive Rescore Pipeline
When a new exploit is confirmed, the retroactive rescore pipeline identifies all entities with significant behavioral overlap, recomputes their scores, and updates the hot layer. Platforms are notified via webhook. This entire process must complete within 4 hours of an exploit being confirmed.

7. Adversarial Resilience
The system’s adversarial threat model assumes that sophisticated attackers will actively attempt to manipulate scores.
7.1 Score Manipulation Attacks
The primary defenses are multi-signal correlation and time-weighted scoring. An adversary who generates artificial safe-looking on-chain transactions will struggle to simultaneously generate authentic off-chain identity signals, genuine market liquidity, and AI-evaluated behavioral patterns consistent with real safe entities. Each individual signal group is gameable in isolation — the combination is not.
7.2 Sybil Identity Attacks
A sybil cluster that all originates from the same deployer address or that routes through the same intermediary address will have that relationship detected by the interaction graph analysis component. The graph-based anomaly detector specifically looks for star-topology interaction patterns as a sybil indicator.
7.3 API Probing Attacks
The API rate limiter applies per-API-key limits with escalating restrictions for query patterns resembling probing. The tiered explainability system ensures that the most granular signal-level information is never returned to public API consumers. Signal-level detail requires an enterprise partnership agreement with contractual restrictions.
7.4 Data Source Poisoning
For on-chain signals, data is collected from multiple independent node providers and cross-validated. A signal that appears in only one provider’s data but not others is quarantined pending investigation. For the exploit signature library specifically, the write-protection and multi-party authorization requirement prevent an API compromise from poisoning ground truth data.
7.5 Behavioral Mimicry
Even a well-executed mimicry attack typically involves a preparation phase where specific signals shift in ways characteristic of attack staging — increasing approval grants, establishing connections with flash loan providers, accumulating target token positions. These staging patterns are detectable by the temporal risk trend analyzer even when the surface-level behavior looks clean.

8. API Layer
The API is the interface between Cencera’s internal intelligence and the consuming platforms. It must be fast, reliable, consistent, and designed so that consuming platforms cannot accidentally misuse it.
8.1 API Design Principles
Every API response includes enough context to be correctly interpreted without requiring the consuming platform to make additional queries. The score manifest, confidence level, lifecycle state, and computation metadata are always present in the response — they cannot be stripped from the payload.
8.2 Core Endpoints
Entity Trust Query — returns the current trust score object for a given entity address and chain. Target response time: under 200 milliseconds at the 99th percentile.
Transaction Risk Context — given a transaction about to be submitted, returns risk context for all entities involved. Used by wallets for pre-transaction warnings. Target response time: under 100 milliseconds.
Batch Screening — accepts up to 500 entity addresses in a single request. Target response time: under 2 seconds.
Historical Reputation Query — returns the score trajectory for an entity over a specified time range. Target response time: under 5 seconds.
Score Webhook Registration — allows platforms to register webhook URLs and conditions. Cencera proactively pushes score updates when a registered entity’s score changes by more than a defined delta or when an entity moves lifecycle states.
Loss Report Submission — accepts user-submitted loss reports with mandatory transaction hash verification.

8.3 Authentication and Access Tiers
Public Tier — no authentication required. Returns composite score, lifecycle state, and category-level breakdown. Rate limited to 100 requests per hour per IP. For developer evaluation only, not production.
Standard Tier — API key authentication. Returns full score object including trajectory, triggered indicators at category level, and computation metadata. Intended for production wallet and tooling integrations.
Enterprise Tier — API key authentication plus contractual agreement. Returns signal-level triggered indicators and feature-level contribution detail. Access to batch screening and webhooks. Custom rate limits and SLA guarantees.

8.4 Response Consistency Guarantees
For any given entity, API key, and timestamp, the same query will always return the same score. A platform that needs to audit why they made a particular decision based on a score can always retrieve the exact score state that existed at the time of that decision.

9. Platform-Level Customization
Different consuming platforms have different risk profiles, user bases, and performance requirements.
9.1 Trust Threshold Configuration
Each platform sets its own trust threshold. Cencera does not enforce thresholds — it provides scores. A DeFi lending protocol with billions in TVL might set a threshold of 80. A consumer wallet might set 60 and display a warning rather than blocking for entities between 40 and 60. Enforcement is always the platform’s responsibility.
9.2 Signal Group Configuration
Platforms can disable signal groups that are not relevant to their use case. When a signal group is disabled, the scoring engine applies adaptive weight normalization and labels the resulting score with a reduced confidence level.
NOTE  Disabling the AI-derived signal group is not permitted for protocols above a defined TVL threshold. The AI layer is the primary detection mechanism for novel attack patterns.
9.3 Lookback Period Configuration
Platforms can set a custom lookback period. The minimum permitted lookback is 30 days. For any entity above a TVL floor with a recommended minimum of $1 million, the scoring engine enforces a minimum lookback of 90 days regardless of platform configuration.
9.4 Alert and Webhook Configuration
Platforms can configure fine-grained conditions under which Cencera pushes proactive alerts: score changes exceeding a defined delta, entities moving to Flagged lifecycle state, entities moving from Nascent to Active state, and retroactive rescore notifications.

10. Operational Architecture
The system serves billion-dollar protocols. The operational architecture describes how the system achieves the reliability, availability, and security standards those protocols require.
10.1 High Availability
The entire system is deployed across a minimum of three availability zones. No single availability zone failure can degrade service below 99.9% availability. The API layer is deployed with global load balancing. The signal store uses synchronous replication across availability zones so that no write is acknowledged until it has been committed in at least two zones.
Each component has a defined fallback behavior when unavailable. Cached scores are always labeled with their staleness age and a Degraded label so consuming platforms know they are working with potentially outdated information.
10.2 Disaster Recovery
Recovery Point Objective: zero data loss for all event log writes. Recovery Time Objective: full service restoration within 15 minutes for any single-component failure, within 60 minutes for a full availability zone failure. These targets are tested quarterly through simulated failure scenarios.
10.3 Security Operations
The production environment is separated from development and staging by hard network boundaries. All API keys are rotated on a 90-day schedule with immediate rotation capability. Any access to the exploit signature library requires a second human operator to authorize. The system undergoes an external security audit at minimum annually, with penetration testing of the API layer every six months.
10.4 Monitoring and Alerting
Automated alerts trigger for: any ingestion worker that has not produced a signal write in the last 10 minutes; any scoring engine latency above 300 milliseconds at the 95th percentile; any anomalous API query pattern matching a probing profile; any attempted write to the exploit signature library without proper authorization; and any retroactive rescore affecting more than 1,000 entities simultaneously.

11. Human Analyst Team Operations
The human analyst team is not a support function. It is a core component of the security architecture.
11.1 The Review Queue
The human review queue is a prioritized list of entities and events requiring analyst attention. Critical items (entities with active Flagged state and high TVL adjacency) have a 4-hour response SLA. Standard items have a 24-hour initial triage SLA and a 72-hour full analysis SLA.
11.2 Analyst Tools and Access
Analysts have access to the full signal history for any entity at signal-level granularity. They have write access to the exploit signature library subject to the multi-party authorization requirement. They do not have write access to the live scoring engine configuration or the API key management system, to prevent a compromised analyst account from being used to manipulate scores in real time.
11.3 Training Data Curation
The highest-leverage activity of the analyst team is the curation of training data. When analysts confirm a new exploit, they document not just the exploit itself but the full behavioral history of the malicious entity in the weeks before the exploit executed. This pre-exploit behavioral fingerprint becomes a training example for the temporal risk trend analyzer.

12. Cross-Chain Architecture
The most sophisticated attackers do not operate on a single chain. Cross-chain reputation is not future work — it is a present requirement.
12.1 Chain-Scoped Scores by Default
By default, every entity score is chain-scoped. An address on Ethereum has an Ethereum score. The same address on Arbitrum has an Arbitrum score. These are separate entities unless explicitly linked.
12.2 Cross-Chain Linkage
Cross-chain linkage is established through cryptographic evidence. When linkage is confirmed, scores influence each other but do not override each other. The influence is asymmetric: negative signals propagate more strongly across chain linkages than positive signals, because the primary threat is an adversary who builds trust on one chain and attacks on another.
12.3 Bridge and Cross-Chain Transaction Risk
Funds that enter the system through a bridge from a chain where the source address has a low trust score carry that risk context with them. The scoring engine tracks bridge provenance for fund flows and applies a provenance risk penalty to entities that receive significant bridged funds from low-trust sources.

13. Integration Architecture for Platform Partners
This section describes the reference integration pattern that Cencera recommends for production integrations.
13.1 Wallet Integrations
For wallet integrations, the primary use case is pre-transaction warnings. The wallet should present category-level risk indicators rather than raw scores, because raw numbers without context are often misinterpreted by end users. Wallet integrations should register webhooks for Flagged state transitions on any entity that the wallet has interacted with.
13.2 DeFi Protocol Integrations
Protocol integrations should use the batch screening endpoint to periodically screen all entities in their active interaction set rather than relying solely on point-in-time queries at interaction time. Cencera should be one input into a protocol’s risk management system, not the entirety of it.
13.3 Security Tool Integrations
Security tools and analytics platforms should make the confidence level and score manifest visible in their UI, not just the composite score number. A tool that presents a 72 trust score without the context that it was computed with a 30-day lookback and two disabled signal groups is misleading users.

14. Known Limitations and Explicit Scope Boundaries
Cencera is designed to be the most comprehensive trust layer in Web3. It is not designed to be infallible.
14.1 What Cencera Does Not Do
Cencera does not prevent transaction execution. It produces scores. Enforcement is always the consuming platform’s responsibility.
Cencera does not replace smart contract audits. Audit reports assess code correctness. Cencera assesses behavioral risk. They answer different questions and are complementary.
Cencera does not eliminate MEV, frontrunning, or oracle manipulation. These are execution-layer phenomena.
Cencera does not guarantee that a high trust score entity is safe. Novel attack types that have never been seen before will not be detected until they are confirmed and added to the training data.

14.2 Inherent Latency in Novel Threat Detection
There is an inherent gap between the moment a new exploit type first appears in the wild and the moment Cencera’s model has been retrained to detect it. The Novel Behavior Flag from the AI layer is the primary mitigation, but it does not eliminate the gap entirely.
14.3 Off-Chain Signal Reliability
Off-chain signals are inherently less reliable than on-chain signals. Social accounts can be faked. GitHub histories can be fabricated. Audit reports can be copied from other projects. The 15% base weight for off-chain signals reflects this lower reliability.

15. Planned Architecture Extensions
15.1 Privacy-Preserving Trust Proofs
A zero-knowledge proof layer that allows entities to prove their trust score meets a threshold without revealing the underlying score or the signals that produced it. This enables privacy-preserving gating in protocols that cannot or should not expose score data in plain text on-chain.
15.2 Community Signal Contributions
A governed mechanism for verified community members to contribute signal data. Community contributions are sandboxed from the primary signal store and require a validation step before being incorporated into scoring. A staking mechanism creates economic incentives for accurate contributions and penalties for false reports.
15.3 On-Chain Trust Attestations
Publishing trust score attestations to a smart contract layer, enabling on-chain composability. A protocol could reference an on-chain Cencera attestation in its own smart contract logic without requiring an API call at transaction execution time.
15.4 Institutional Grade Reporting
A regulatory reporting module for institutional platforms that need auditable records of all trust-based decisions in a format suitable for submission to financial regulators.

16. Business Economics — Pricing, Speed, Cost & Margins
This section answers five critical business questions: what to charge per API call, the expected response latency at each tier, how accuracy compares to competitors, what each API call costs to serve, and what profit margin the business can realistically achieve.
16.1 Recommended Pricing Structure
Blockaid, the closest comparable, charges $0.0001 to $0.0005 per call for binary transaction screening. Cencera is not doing binary screening — it is doing longitudinal, multi-signal behavioral analysis with explainable outputs. The premium over Blockaid is justified if and only if accuracy numbers hold after 6 to 12 months of production data, and early enterprise contracts must be priced to reflect that Cencera is proving its model, not just selling infrastructure.
Pricing is structured by call type, not as a flat per-call rate, because the cost to serve is radically different for a cached trust query versus a full fresh scoring run.

Critical Observations on the Economics
The fastest path to breakeven is not API volume — it is enterprise contracts. A single signed deal at $15,000 per month covers months of infrastructure cost. Three enterprise deals at $20,000 per month put the business at breakeven before public API volume is meaningful.
Fixed costs do not scale linearly with volume. The ingestion pipeline, database replication, and analyst team costs grow at a fraction of the rate that revenue grows as volume increases. This is where operating leverage comes from.
The LLM cost is not the problem. At Haiku-class pricing, AI inference is under $0.000005 per call. Teams that assume AI = expensive per-call cost are wrong. The RPC data cost for fresh scoring runs is the real variable to optimize, not the model inference.
Wallet integrations (Phantom, MetaMask, Trust Wallet) will generate the highest call volumes but at lower per-call revenue. Protocol integrations (Uniswap, Aave) will generate lower volumes but higher per-call revenue and predictable monthly contracts. Build for both but sell to protocols first.
The background scoring pipeline is a capital investment, not a cost. Every dollar spent keeping scores warm in the hot layer reduces the cost of a production API call by a factor of 10 to 40. Do not underfund this.
